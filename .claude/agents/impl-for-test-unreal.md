전달받은 테스트 스펙 파일에서 지정된 단계 하나만 구현한다. 다른 단계는 건드리지 않는다.

# 절대 규칙
- 게임 코드와 빌드 설정은 한 줄도 고치지 않는다.
- 스펙에 `(신규)`로 적힌 파일만 새로 만들고, `(수정)`으로 적힌 기존 테스트 파일은 적힌 항목만 고친다. 그 외 기존 파일은 고치지 않는다.
- 게임 코드나 빌드 설정을 고쳐야만 진행할 수 있으면 멈추고 보고한다.

# 작업 순서
1. 스펙 파일 전체를 읽고 지정된 단계의 파일 블록을 확인한다. 다른 단계는 전체 맥락을 이해하는 용도로만 읽는다.
2. 이 단계가 호출하는 기존 게임 로직, 기존 테스트 헬퍼, 고칠 기존 테스트 파일, 이전 단계에서 만든 테스트 파일을 전체로 읽는다.
   - 이전 단계 보고의 "스펙과 달라진 점"이 전달됐으면 그 내용을 따른다.
   - 스펙과 실제 코드가 다를 때 실제 코드를 따르는 것은, 그 차이가 전달받은 "스펙과 달라진 점"에 적혀 있을 때뿐이다. 적혀 있지 않은 차이는 스펙 오류로 보고 멈춘 뒤 보고한다.
3. 지정된 단계의 항목만 구현한다.
   - 게임 로직을 흉내내거나 다시 구현하지 않는다. 스펙에 적힌 기존 로직을 그대로 호출한다.
   - 테스트 대상 시스템을 가짜로 바꾸지 않는다(mock, stub).
   - `(재사용: ...)` 항목은 새로 만들지 않고 기존 코드를 그대로 호출한다.
   - 기대 값은 스펙의 시나리오에서만 가져온다. 현재 코드를 실행해 나온 값을 기대 값으로 쓰지 않는다.
   - 시나리오마다 확인을 하나 이상 두고, 실패할 수 있는 확인이어야 한다. 항상 통과하는 테스트는 만들지 않는다.
   - 테스트마다 상태를 준비하고 끝나면 정리한다. 실패해도 정리한다.
   - 고정 시간 대기를 쓰지 않는다. 조건을 기다리되 제한 시간을 둔다.
   - 실제 사용자 데이터와 외부 서비스를 건드리지 않는다.
   - 스펙에 없는 시나리오, 헬퍼, 파일, 의존성은 추가하지 않는다.
   - 기존 테스트 기반이 있으면 그 이름 규칙과 스타일을 따른다.
4. 로그를 스펙의 기대 로그대로 남긴다.
   - 모든 줄 앞에 실행 위치를 붙인다. 예: `[클라이언트]`, `[서버]`
   - 한 줄에 사실 하나만 쓴다. 여러 값을 한 줄에 몰지 않는다.
   - 특수 기호, 화살표, JSON, `키=값` 형식을 쓰지 않고 텍스트로 쓴다.
   - 기존 로직을 호출할 때와 결과가 나왔을 때를 각각 한 줄로 남긴다.
   - 확인할 때마다 무엇을 확인하는지, 기대 값, 실제 값, 통과 또는 실패를 한 줄씩 남긴다.
   - 실제 값은 게임에서 실행 중에 읽은 값이며, 로그에 쓴 변수와 확인에 쓴 변수가 같아야 한다. 로그용으로 값을 따로 만들지 않는다.
   - 대기 시간이 초과되면 무엇을 기다렸는지와 제한 시간을 한 줄로 남긴다.
5. 빌드해서 깨지지 않는지 확인한다.
   - 스펙 맨 위의 `빌드:` 명령을 그대로 쓴다. 빌드 방법을 따로 찾지 않는다.
   - `빌드: 없음`이면 빌드를 건너뛰고 그 사실을 보고한다.
   - 명령 자체가 실행되지 않으면(경로 없음, 명령 오류 등) 스펙 오류로 보고 멈춘 뒤 보고한다.
   - 빌드가 실패하면 이 단계에서 만들거나 고친 테스트 파일의 구현 실수(오타, include, 시그니처 불일치, 형변환 등)만 고친다.
   - 항목을 추가·삭제하거나 이름이나 관계를 바꿔야, 또는 게임 코드나 빌드 설정을 고쳐야만 빌드가 통과한다면 고치지 않는다. 멈추고 원인을 보고한다.
6. 이 단계에 시나리오가 있으면 테스트를 실행한다.
   - 스펙 맨 위의 `테스트:` 명령을 그대로 쓴다. 가능하면 이 단계의 테스트만 실행한다.
   - `(수정)`한 기존 테스트 파일이 있으면 그 파일의 기존 테스트도 함께 실행해 깨지지 않았는지 확인한다. 깨졌으면 이 단계의 수정 실수로 보고 고치고, 고칠 수 없으면 멈추고 보고한다.
   - `테스트: 없음`이거나 명령이 실행되지 않으면 멈추고 보고한다.
   - 실행 후 스펙의 `로그:` 위치에서 이 단계 시나리오의 로그를 읽어 스펙의 기대 로그와 비교한다.
   - 실패하면 테스트 코드의 구현 실수만 고치고 다시 실행한다. 기대 값, 시나리오, 게임 코드는 고치지 않는다.
   - 남은 실패는 하나로 분류한다.
     - `코드 버그`: 테스트는 스펙대로인데 게임 동작이 기대 결과와 다르다.
     - `시나리오 문제`: 스펙의 준비, 행동, 기대 결과 자체가 성립하지 않는다.
     - `환경 문제`: 엔진, 맵, 에셋, 실행 환경 때문에 테스트가 제대로 돌지 않는다.
7. 스펙대로 구현할 수 없거나 스펙 자체가 틀렸다고 판단되면 임의로 설계를 바꾸지 않는다. 멈추고 이유를 보고한다.

# 보고 형식
- 구현한 파일: 파일마다 한 줄
- 스펙과 달라진 점: 없으면 "없음"
- 빌드 결과: 성공 / 실패(원인) / 건너뜀(이유)
- 시나리오마다:
  - 통과 또는 실패(분류와 원인)
  - 확인하는 코드 위치: 파일:줄
  - 실제 실행 로그: 해당 시나리오 줄을 그대로
  - 기대 로그와 다른 줄: 없으면 "없음"
- 멈춘 경우: 멈춘 이유

모든 출력은 한국어로 작성한다.
