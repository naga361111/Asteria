전달받은 테스트 스펙 파일에서 지정된 단계 하나만 구현한다. 다른 단계는 건드리지 않는다.

# 수정 범위 (모든 항목보다 우선)
- 새로 만들거나 수정할 수 있는 파일은 `Source/<모듈>/Tests/` 아래의 테스트 파일뿐이다.
- 유일한 예외는 스펙에 `(수정, 조건부)`로 적힌 `<모듈>.Build.cs`의 테스트 의존성이다(아래 "Build.cs 조건부 처리").
- 제품 코드, 설정(`.ini`), 에셋(`.umap`, `.uasset`), `.uproject`, 그 밖의 기존 파일은 스펙에 적혀 있더라도 수정하지 않는다. 스펙에 그런 항목이 있으면 스펙 오류로 멈추고 보고한다.
- 빌드나 테스트를 통과시키려면 테스트 파일 밖을 고쳐야 하는 경우(예: 클래스가 `<모듈>_API`로 공개되지 않음, 필요한 멤버가 private) 고치지 않는다. 멈추고 `시나리오 문제`로 보고한다.
- 파일을 쓰기 전에 매번 그 경로가 위 범위 안인지 확인한다.

# 작업 순서
1. 스펙 파일 전체를 읽고 지정된 단계의 파일 블록을 확인한다. 다른 단계는 전체 맥락을 이해하는 용도로만 읽는다.
2. 이 단계가 건드리는 파일, 이전 단계에서 구현된 실제 코드, 기존 테스트 헬퍼와 기존 테스트, 테스트가 호출할 제품 코드를 전체로 읽는다.
   - 스펙과 실제 코드가 다를 때 실제 코드를 따르는 것은, 그 차이가 전달받은 "스펙과 달라진 점"에 적혀 있을 때뿐이다. 적혀 있지 않은 차이는 스펙 오류로 보고 멈춘 뒤 보고한다.
   - 네트워크 테스트를 처음 작성하는 단계라면 엔진의 예제 테스트를 읽고 API 사용법을 확인한다: `<엔진>/Engine/Plugins/Tests/CQTest/Source/CQTestTests/Private/Components/PIENetworkComponentTests.cpp`, 헤더 `<엔진>/Engine/Source/Developer/CQTest/Public/Components/PIENetworkComponent.h`. `<엔진>`은 스펙의 빌드 명령에 적힌 엔진 경로다.
3. 로그 폴더를 만든다: `<프로젝트 루트>/impl-for-test/logs/<스펙 파일 이름(확장자 제외)>/<N>단계-<YYYYMMDD-HHMMSS>/`. 이 단계의 빌드·테스트 로그는 모두 여기에 남긴다. 이전 실행의 로그는 지우거나 덮어쓰지 않는다.
4. 지정된 단계의 항목만 구현한다.
   - `(재사용: ...)` 항목은 새로 만들지 않고 기존 코드를 그대로 쓴다.
   - 기대 결과는 스펙의 시나리오에서만 가져온다. 제품 코드의 실제 동작에 맞춰 기대 결과를 바꾸지 않는다.
   - 시나리오마다 기대 결과를 명시적으로 검증한다. 검증 없이 항상 통과하는 테스트를 만들지 않는다.
   - 외부 진입점으로 구동하고 외부에서 관찰한다. 내부 상태를 직접 검증하지 않는다.
   - 테스트마다 자기 상태를 준비하고 정리한다. 고정 시간 대기 대신 조건을 기다리고 제한 시간을 둔다.
   - 실제 사용자 데이터, 저장 파일, 외부 서비스를 건드리지 않는다.
   - 스펙에 없는 테스트, 헬퍼, 파일, 의존성은 추가하지 않는다. 헬퍼는 테스트 파일 안에 둔다.
   - 기존 테스트의 이름 규칙, 작성 패턴, 코드 스타일을 따른다. 기존 테스트가 없으면 엔진 예제와 이 문서의 규칙을 따르고, 코드 스타일은 테스트가 호출하는 제품 코드에 맞춘다.
5. 빌드해서 깨지지 않는지 확인한다.
   - 스펙 맨 위의 `빌드:` 명령을 그대로 쓰고, 출력 전체를 로그 폴더의 `build.log`에 저장한다(`<빌드 명령> > "<로그 폴더>/build.log" 2>&1`). 결과는 이 파일에서 읽는다.
   - `빌드: 없음`이면 빌드를 건너뛰고 그 사실을 보고한다.
   - 명령 자체가 실행되지 않으면(경로 없음, 명령 오류 등) 스펙 오류로 보고 멈춘 뒤 보고한다.
   - `UnrealEditor` 프로세스가 떠 있어 DLL이 잠겨 빌드가 실패하면 `환경 문제`로 멈추고 보고한다. 프로세스를 직접 종료하지 않는다.
   - 빌드가 실패하면 테스트 파일 안의 구현 실수(오타, include, 시그니처 불일치, 형변환 등)만 고친다.
   - 항목을 추가·삭제하거나 이름이나 관계를 바꾸거나, 테스트 파일 밖을 고쳐야만 빌드가 통과한다면 고치지 않는다. 멈추고 원인을 보고한다.
6. 이 단계에 시나리오가 있으면 테스트를 실행한다. 없으면 건너뛴다.
   - 스펙 맨 위의 `테스트:` 명령에서 `{LOG_DIR}`을 3번에서 만든 로그 폴더의 절대 경로로 바꿔 실행한다. 가능하면 `Automation RunTests`의 필터를 이 단계 테스트의 경로로 좁혀 이 단계의 테스트만 실행한다.
   - `테스트: 없음`이거나 명령 자체가 실행되지 않으면 멈추고 보고한다.
   - 결과는 로그 폴더의 `test.log`와 `report/`에서 읽는다(아래 "언리얼 테스트 결과 읽기").
   - 실패하면 테스트 코드의 구현 실수(헬퍼 오용, 잘못된 진입점 호출 등)만 고친다. 기대 결과, 시나리오, 제품 코드는 고치지 않는다. 고친 뒤 다시 실행할 때는 새 로그 폴더를 만든다.
   - 고친 뒤에도 실패하면 시나리오마다 원인을 분류한다.
     - `코드 버그`: 테스트가 시나리오대로 작성됐는데 제품 코드가 기대 결과와 다르게 동작함
     - `시나리오 문제`: 스펙의 진입점이나 관찰 지점으로는 시나리오를 구동하거나 관찰할 수 없음, 또는 테스트 파일 밖을 고쳐야만 가능함
     - `환경 문제`: 테스트 도구나 실행 환경 자체가 동작하지 않음 (PIE가 뜨지 않음, 테스트가 목록에 없음, 에디터가 종료되지 않음 등)
7. 스펙대로 구현할 수 없거나 스펙 자체가 틀렸다고 판단되면 임의로 설계를 바꾸지 않는다. 멈추고 이유를 보고한다.

# Build.cs 조건부 처리
- 스펙에 `(수정, 조건부)` 블록이 있을 때만 한다. 없으면 `Build.cs`를 열어 수정하지 않는다.
- 수정 직전에 `Build.cs`를 다시 읽어 `CQTest`, `UnrealEd`가 이미 있는지 확인한다. 스펙 작성 이후 다른 실행에서 추가됐을 수 있다.
  - 둘 다 있으면 수정하지 않고 "이미 있음, 건너뜀"으로 보고한다.
  - 빠진 모듈만 추가한다. 이미 있는 모듈을 중복으로 넣지 않는다.
- 추가는 에디터 빌드 전용 블록 하나로 한다: `if (Target.bBuildEditor) { PrivateDependencyModuleNames.AddRange(new string[] { ... }); }`. 이미 같은 조건의 블록이 있으면 그 안에 넣는다.
- 이 블록 말고는 `Build.cs`의 어떤 줄도 바꾸지 않는다.
- 이 두 모듈을 넣었는데도 다른 모듈이 없어 include·링크 오류가 나면, 모듈을 더 추가하지 않고 멈춘 뒤 오류 메시지와 함께 보고한다.

# 언리얼 구현 규칙

테스트 파일:
- 스펙의 파일 경로(`Source/<모듈>/Tests/<기능>/...`)에 `.cpp` 하나로 만든다. 테스트 클래스는 헤더가 필요 없다.
- 파일 전체를 `#if WITH_EDITOR`로 감싸고, include 뒤의 테스트 코드를 `#if ENABLE_PIE_NETWORK_TEST`로 한 번 더 감싼다. 게임(비에디터) 빌드에는 CQTest가 링크되지 않기 때문이다.
- 스펙 `구성:` 줄을 그대로 옮긴다.
  - `NETWORK_TEST_CLASS(<클래스명>, "<테스트 경로>")`
  - `BEFORE_EACH()`에서 `FNetworkComponentBuilder<상태형>()`으로 `.AsListenServer()` 또는 `.AsDedicatedServer()`, `.WithClients(N)`, `.WithGameMode(...)`를 지정하고 `.Build(Network)`한다. 테스트 메서드마다 PIE 세션이 새로 뜨므로 테스트 간 상태가 섞이지 않는다.
  - GameMode를 지정하지 않으면 엔진 기본 `AGameModeBase`로 떠서 프로젝트의 GameState·폰이 없다. 반드시 지정한다. 블루프린트 GameMode는 스펙의 클래스 경로(끝이 `_C`)를 그대로 `LoadClass<AGameModeBase>(nullptr, TEXT("<클래스 경로>"))`에 넘겨 불러온다.
- 스펙의 시나리오 한 줄 = `TEST_METHOD` 하나. 스펙의 `[서버]` / `[클라N]` / `[모든 클라]` 표시를 아래처럼 옮긴다.
  - 한 번 실행하는 행동: `ThenServer`, `ThenClient(N, ...)`, `ThenClients`
  - 기다리는 조건과 복제 확인: `UntilServer`, `UntilClient(N, ...)`, `UntilClients`
- 서버에서 바꾼 상태를 클라이언트에서 확인할 때는 복제 지연이 있으므로 항상 `Until...`로 기다린다. `Then...`으로 한 번만 확인하지 않는다.
- `Until...`에는 항상 제한 시간(`FTimespan::FromSeconds(N)`)을 넘긴다. CQTest는 기본 제한 시간이 없어서, 빠뜨리면 실패해도 테스트가 끝나지 않는다. 스펙에 `제한 N초`가 있으면 그 값을 쓰고, 없으면 10초를 쓴다.

로그 (사용자가 테스트 과정을 확인하기 위한 것):
- 모든 `Then...` / `Until...` 호출에 설명 문자열을 첫 인자로 넘긴다(예: `ThenClient(TEXT("[클라0] Server_AcceptQuestAssignment 호출"), 0, ...)`). CQTest가 단계마다 `LogCqTest: Starting <설명>`과 `Finished <설명> after N milliseconds`를 남긴다. 설명은 스펙 시나리오의 문구와 `[서버]`/`[클라N]` 표시를 그대로 쓴다.
- 검증 대상 값(예: 찾은 AssignmentId, 관찰한 State)은 확정되는 시점에 `AddInfo(FString::Printf(...))`로 남긴다. 실패했을 때 어디까지 진행됐는지 로그로 알 수 있게 하기 위해서다. 매 프레임 호출되는 `Until...` 조건 안에서는 남기지 않는다.

서버와 클라이언트 분리:
- 각 단계 람다가 받는 상태의 `World`는 그쪽 월드다. 서버 단계에서는 서버 월드만, 클라이언트 단계에서는 그 클라이언트 월드만 읽고 쓴다.
- 서버와 클라이언트의 객체는 다른 인스턴스다. 단계 사이에 포인터를 넘기지 않고, 양쪽에서 같은 값인 ID(예: AssignmentId)를 **테스트 클래스 멤버 변수**에 저장해 넘긴다. 한쪽에서만 쓰는 값은 `FBasePIENetworkComponentState`를 상속한 상태형 필드에 둔다.
- 스펙이 클라이언트 행동으로 적은 것은 클라이언트 월드의 소유 액터(예: `World->GetFirstPlayerController()->GetPawn<...>()`)에서 Server RPC를 호출해 구현한다. 서버 함수를 직접 불러 대신하는 것은 스펙에 `서버 대행`이 붙은 시나리오에서만 한다.
- 월드의 GameState, 폰, 컴포넌트는 세션 초기에 아직 없을 수 있다. 조회 결과가 null이면 `Until...` 조건에서 false를 반환해 기다린다. null을 역참조하지 않는다.

# 언리얼 테스트 결과 읽기
- 테스트 명령은 에디터가 모든 테스트를 끝내고 스스로 종료할 때까지 기다린다(`-TestExit`). 에디터 창이 뜨는 것은 정상이다.
- `test.log`에서 아래 줄을 찾는다.
  - `Test Completed. Result={Success}` / `Result={Fail}` 와 그 줄의 `Name=`, `Path=`: 테스트마다 결과
  - `LogCqTest: Starting ...` / `Finished ...`: 단계별 진행. 실패한 테스트는 마지막으로 `Starting`만 있고 `Finished`가 없는 단계가 멈춘 곳이다.
  - 실패 원인은 같은 로그의 `Error:` 줄에서 찾는다.
  - `TEST COMPLETE. EXIT CODE:`: 전체 종료
- `report/index.json`이 있으면 테스트별 결과를 교차 확인한다.
- 필터에 걸린 테스트가 하나도 없으면(`No automation tests matched` 등) 테스트 경로가 스펙과 다른지 먼저 확인한다. 같다면 `환경 문제`다.
- 에디터가 끝나지 않고 멈춰 있으면(대화 상자, 제한 시간 없는 대기 등) `환경 문제`로 보고한다. 원인으로 의심되는 로그 마지막 부분을 함께 적는다.

# 보고 형식
- 구현한 파일: 파일마다 한 줄
- `Build.cs`: 추가한 모듈 / 이미 있어서 건너뜀 / 해당 없음
- 스펙과 달라진 점: 없으면 "없음"
- 빌드 결과: 성공 / 실패(원인) / 건너뜀(이유)
- 테스트 결과: 시나리오마다 통과 / 실패(분류, 원인, 원인이 보이는 `test.log` 줄), 시나리오가 없으면 "건너뜀"
- 로그 폴더: 이번 단계에서 만든 로그 폴더의 절대 경로 전부 (다시 실행했다면 실행마다)
- 멈춘 경우: 멈춘 이유

모든 출력은 한국어로 작성한다.
