다음 기능의 E2E 테스트 스펙을 작성하고, 저장한 뒤, 단계별로 구현한다. 스펙 작성 중에는 코드를 작성하지 않는다.

요청: $ARGUMENTS

# 0. 절대 규칙
- 게임 코드와 빌드 설정은 한 줄도 고치지 않는다.
- 테스트는 새 테스트 파일로 만들거나 기존 테스트 파일을 고쳐서 만든다. 기존 테스트 파일은 스펙에 `(수정)`으로 적은 경우에만 고친다.
- 테스트 코드는 이미 작성된 게임 로직을 호출하고 결과를 확인하는 것이 전부다.
- 게임 코드나 빌드 설정을 고쳐야만 테스트할 수 있는 시나리오는 스펙에 넣지 않는다. 7번 항목에서 이유와 함께 따로 알린다.

# 1. 코드베이스 분석
- 테스트할 기능의 파일을 발췌가 아니라 전체로 읽고, 실제 호출 흐름을 처음부터 끝까지 따라간다.
- 테스트가 호출할 진입점(외부에서 부를 수 있는 기존 함수, 이벤트, 명령)과 결과를 읽을 수 있는 지점(상태, 값, 이벤트)을 찾는다.
- 기존 테스트 기반(프레임워크, 헬퍼, 로그 방식, 이름 규칙)이 있는지 검색한다.
- 프로젝트의 기존 로그 출력 방식과 로그가 기록되는 위치를 찾는다.
- 빌드 명령과 테스트 실행 명령을 각각 그대로 실행할 수 있는 한 줄로 정리한다. 찾지 못하면 `없음`으로 둔다.

# 2. 설계 (판단 순서)
항목마다 아래 순서로 따지고, 처음으로 성립하는 단계에서 멈춘다.
1. 요청한 동작을 검증하는 데 정말 필요한가? 추측성 필요라면 넣지 않는다.
2. 기존 테스트 기반이나 헬퍼에 이미 있는가? 있으면 그대로 호출한다. 기존 테스트 파일을 조금 고쳐서 되면 새로 만들지 않고 고친다.
3. 엔진/프레임워크의 테스트 기능으로 되는가? 그걸 쓴다.
4. 이미 설치된 의존성으로 되는가? 그걸 쓴다. 새 의존성은 추가하지 않는다.
5. 여기까지 안 되면 동작하는 최소 구조로 만든다.

시나리오 범위:
- 요청한 동작마다 정상 흐름 하나.
- 요청한 동작에 검증, 권한, 오류 처리가 있으면 그것마다 실패 흐름 하나.
- 모든 조합을 나열하지 않는다.

금지:
- 게임 로직을 테스트 안에서 흉내내거나 다시 구현하는 것. 반드시 기존 로직을 호출한다.
- 테스트 대상 시스템을 가짜로 바꾸는 것(mock, stub)
- 내부 구현을 직접 들여다보는 검증. 결과를 읽을 수 있는 지점에서만 확인한다.
- 고정 시간 대기. 조건을 기다리되 제한 시간을 둔다.
- 한 번만 쓰는 추상화, "나중을 위한" 뼈대, 필요 이상의 파일 분리

반드시 유지:
- 테스트마다 자기 상태를 준비하고 끝나면 정리한다. 다른 테스트의 결과에 기대지 않는다.
- 실제 사용자 데이터와 외부 서비스를 건드리지 않는다.
- 요청에 명시된 모든 동작

기대 결과:
- 기대 결과는 요청에서 가져온다. 요청에 없어 현재 코드의 동작에서 가져온 기대 결과에는 `코드 기준`을 붙인다.

# 3. 로그 규칙
- 테스트 전용 로그 헬퍼를 둔다. 기존 테스트 기반에 쓸 만한 로그 헬퍼가 있으면 그대로 호출하고, 없으면 기존 로그 방식 위에 얹어 만든다.
- 모든 로그 줄 앞에 실행 위치를 붙인다. 예: `[클라이언트]`, `[서버]`. 구분이 없는 프로젝트는 `[테스트]`.
- 한 줄에는 사실 하나만 쓴다. 여러 값을 한 줄에 몰지 않고 줄을 나눈다.
- 특수 기호, 화살표, JSON, `키=값` 형식을 쓰지 않는다. 문장처럼 텍스트로 쓴다. 숫자는 그대로 쓴다.
- 기존 로직을 호출할 때와 그 결과가 나왔을 때를 각각 한 줄로 남긴다. 예: `[클라이언트] 경비병 이동 시작` 다음 `[클라이언트] 경비병 이동 완료`
- 확인할 때마다 네 줄을 남긴다: 무엇을 확인하는지, 기대 값, 실제 값, 통과 또는 실패.
- 실제 값은 게임에서 실행 중에 읽은 값이어야 하며, 로그에 쓴 값과 확인에 쓴 값은 같은 변수여야 한다.
- 대기 시간이 초과되면 무엇을 기다렸는지와 제한 시간을 한 줄로 남긴다.

이 로그가 검증 추적 수단이다. 스펙의 기대 로그와 실제 실행 로그를 비교해, 기존 로직이 실제로 호출됐는지와 실제 값을 읽어 확인했는지를 사용자가 추적한다. 추적을 위한 별도 테스트 로직은 만들지 않는다.

# 4. 저장 전 자기 점검
스펙을 저장하기 전에 모든 항목을 다시 확인한다.
- `(수정)` 블록이 모두 기존 테스트 파일인지 확인한다. 게임 코드나 빌드 설정을 고치는 항목이 있으면 그 시나리오를 빼고 7번 항목에서 알린다.
- 기존 테스트 파일을 고쳐도 그 파일의 기존 테스트가 깨지지 않는지 확인한다.
- 같은 역할의 헬퍼가 기존 테스트 기반에 이미 있는지 다시 검색한다. 있으면 재사용으로 바꾼다.
- 판단 순서 1단계(정말 필요한가)를 다시 적용한다. 통과하지 못하면 지운다.
- 시나리오마다 호출할 기존 로직과 결과를 읽을 지점이 실제로 존재하는지 확인한다.
- 시나리오마다 확인 로그가 하나 이상 있는지, 기대 값이 구체적인지 확인한다.
- 재사용 항목의 위치가 실제로 존재하고, 호출하는 이름이 양쪽 파일에서 일치하는지 확인한다.
- 새 파일을 추가하는 것만으로 빌드에 포함되는지 확인한다. 빌드 설정을 고쳐야 한다면 해당 시나리오를 빼고 7번 항목에서 알린다.
- 각 단계가 끝났을 때 빌드가 깨지지 않는지 확인한다. 깨지면 단계를 다시 나눈다.
- 빌드 명령과 테스트 명령에 쓰인 경로가 실제로 존재하는지 확인한다.

# 5. 스펙 형식
- 파일 맨 위에 다음 네 줄을 쓰고 빈 줄을 둔다. 그 외에는 단계 표시와 파일 블록만 쓴다.
  - `요청: <요청 원문>`
  - `빌드: <빌드 명령 또는 없음>`
  - `테스트: <테스트 실행 명령 또는 없음>`
  - `로그: <실행 로그가 기록되는 위치>`
- 파일 블록을 구현 단계별로 묶는다. 단계마다 첫 줄에 `[N단계]`를 쓰고, 그 아래에 해당 파일 블록을 둔다.
  - 로그 헬퍼처럼 다른 파일이 호출하는 파일을 먼저 둔다.
  - 같은 단계 안의 파일끼리는 서로 의존하지 않는다.
  - 단계 사이는 빈 줄 두 개로 구분한다.
- 파일마다 블록 하나를 만든다. 첫 줄은 파일 이름과 상태다.
  - 예: `NpcMoveTest.cpp (신규)`, `NpcTestHelpers.cpp (수정)`. `(수정)`은 기존 테스트 파일에만 쓴다.
- 헬퍼 항목은 한 줄에 하나씩 쓴다.
  - 형식: `이름: 역할 설명 - 관계 (상태)`
  - 상태: `신규` / `수정` / `재사용: 파일경로`
- 시나리오는 한 줄에 하나씩 쓰고, 그 아래에 기대 로그를 두 칸 들여써서 한 줄씩 쓴다.
  - 형식: `이름: 준비, 행동, 기대 결과 - 호출하는 기존 로직과 경로 (신규 또는 수정, 정상 또는 예외)`
  - 기대 결과를 현재 코드에서 가져왔으면 `코드 기준`을 붙인다. 예: `(신규, 예외, 코드 기준)`
  - 실행 중에 읽는 값은 `{실제 X}`처럼 중괄호로 비워 둔다.
- 블록 사이는 빈 줄로 구분한다.
- 무엇을 하는지만 쓰고, 어떻게 하는지는 쓰지 않는다. 코드, 함수 본문, 의사 코드는 넣지 않는다.

형식 예시:

요청: 경비병 NPC가 지정한 위치까지 이동하는지 테스트
빌드: <빌드 명령>
테스트: <테스트 실행 명령>
로그: Saved/Logs/Game.log

[1단계]
TestLog.h / .cpp (신규)
Log(): 실행 위치를 앞에 붙여 한 줄을 기록 - UE_LOG 호출 (신규)
LogCheck(): 확인 대상, 기대 값, 실제 값, 결과를 네 줄로 기록 - Log() 호출 (신규)


[2단계]
NpcMoveTest.cpp (신규)
MoveToTarget: 빈 맵에 경비병을 생성, 목표 위치로 이동 명령, 목표 위치에 도착 - SpawnNpc() 호출 (재사용: Source/Game/NpcSpawner.cpp), MoveTo() 호출 (재사용: Source/Game/NpcAI.cpp) (신규, 정상)
  [클라이언트] 경비병 생성
  [클라이언트] 경비병 이동 시작
  [클라이언트] 경비병 이동 완료
  [클라이언트] 경비병 위치 확인
  [클라이언트] 기대 위치 X 1000 Y 500
  [클라이언트] 실제 위치 X {실제 X} Y {실제 Y}
  [클라이언트] 통과
MoveToBlocked: 벽으로 막힌 목표 위치로 이동 명령, 이동 실패를 알림 - MoveTo() 호출 (재사용: Source/Game/NpcAI.cpp) (신규, 예외, 코드 기준)
  [클라이언트] 경비병 생성
  [클라이언트] 경비병 이동 시작
  [클라이언트] 경비병 이동 결과 확인
  [클라이언트] 기대 결과 실패
  [클라이언트] 실제 결과 {실제 결과}
  [클라이언트] 통과

# 6. 스펙 저장
- 프로젝트 루트는 `git rev-parse --show-toplevel`의 결과로 정한다. git 저장소가 아니면 현재 작업 디렉토리를 쓴다.
- 프로젝트 루트 아래 `impl-for-test/` 폴더에 `YYYY-MM-DD-<기능-이름>.md`로 저장한다. 폴더가 없으면 만든다.
  - `<기능-이름>`은 기능을 나타내는 짧은 영어 kebab-case 이름이다. 예: `2026-09-24-npc-move.md`
  - 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 끝에 `-2`, `-3`을 붙인다.

# 7. 구현 전 승인
- 저장한 스펙 파일의 경로와 전체 내용을 출력한다.
- `코드 기준` 시나리오를 따로 모아 보여준다. 현재 코드가 틀렸다면 이 테스트도 틀린 동작을 기대하게 된다.
- `(수정)`하는 기존 테스트 파일과 고치는 항목을 따로 보여준다. 없으면 생략한다.
- 게임 코드나 빌드 설정을 고쳐야 해서 뺀 시나리오를 이유와 함께 따로 보여준다. 없으면 생략한다.
- AskUserQuestion으로 구현 진행 여부를 묻는다. 선택지:
  - `구현 진행`: 8번 항목(단계별 구현)으로 넘어간다.
  - `중단`: 스펙 파일 경로만 알리고 끝낸다.
- 사용자가 직접 입력으로 수정 요청을 주면, 스펙을 고쳐 같은 파일에 다시 저장한다. 4번 항목(저장 전 자기 점검)을 다시 거친 뒤, 바뀐 내용을 출력하고 같은 질문을 다시 묻는다.
- 사용자가 스펙 파일을 직접 고쳤을 수 있으므로, 승인 후에는 파일을 다시 읽어 최신 내용을 기준으로 삼는다.

# 8. 단계별 구현
- 저장한 스펙 파일의 1단계부터 순서대로, 단계마다 Agent 도구로 `impl-for-test-base` 서브 에이전트를 하나씩 호출한다. `run_in_background: false`로 호출해 이전 단계가 완전히 끝난 뒤 다음 단계를 시작한다.
- 각 호출에 넘기는 프롬프트:
  - 스펙 파일의 절대 경로
  - 구현할 단계 번호
  - 이전 단계 보고서의 "스펙과 달라진 점" (1단계는 없음)
- 서브 에이전트가 빌드 실패, 구현 불가, 테스트 실행 불가, `시나리오 문제`, `환경 문제`를 보고하면 다음 단계로 넘어가지 않고 멈춘다.
- `코드 버그`는 멈추지 않는다. 최종 보고에 모은다.
- 스펙 자체를 고쳐야 하는 문제가 보고되면 스스로 고치지 않고 멈춘다.

# 9. 최종 보고
- 스펙 파일 경로, 테스트 실행 명령, 로그 위치
- 단계마다: 구현한 파일, 스펙과 달라진 점, 빌드 결과
- 시나리오마다: 통과 또는 실패, 실패 분류, 확인하는 코드 위치(파일:줄), 실제 실행 로그
- 스펙의 기대 로그와 실제 로그가 다른 시나리오
- 발견한 `코드 버그` 목록
- 멈췄다면 멈춘 단계와 원인

모든 출력은 한국어로 작성한다.
