다음 기능의 E2E 테스트 스펙을 작성하고, 저장한 뒤, 단계별로 구현한다. 스펙 작성 중에는 코드를 작성하지 않는다.

요청: $ARGUMENTS

# 0. 수정 범위 (모든 항목보다 우선)
- 테스트 구현은 **테스트 파일만** 새로 만들거나 수정한다. 테스트 파일은 `Source/<모듈>/Tests/` 아래의 파일이다.
- 제품 코드, 설정(`.ini`), 에셋(`.umap`, `.uasset`), `.uproject`, 그 밖의 기존 파일은 수정하지 않는다.
- 유일한 예외는 `<모듈>.Build.cs`의 테스트 의존성이다. 이미 있으면 건드리지 않고, 빠진 것만 한 번 추가한다(2번 항목 "테스트 의존성").
- 기존 진입점으로 구동하거나 관찰할 수 없는 시나리오는 제품 코드를 고쳐서 가능하게 만들지 않는다. 스펙에서 빼고, 승인 때 `제외한 시나리오`로 이유와 함께 보여준다.

# 1. 코드베이스 분석
- 테스트 대상 기능의 코드를 발췌가 아니라 전체로 읽고, 외부 입력부터 결과까지 실제 흐름을 따라간다.
- 테스트가 기능을 구동할 수 있는 외부 진입점(입력, 공개 API, 명령, 네트워크 등)과, 결과를 밖에서 관찰할 수 있는 지점을 찾는다.
  - 테스트 파일은 다른 파일에 있으므로, 진입점과 관찰 지점이 테스트 파일에서 접근 가능한지(public 멤버인지, 클래스가 `<모듈>_API`로 공개됐는지) 확인한다.
- 기존 테스트 기반을 파악한다: 테스트 프레임워크, 헬퍼, 픽스처, 기존 테스트의 위치와 이름 규칙과 작성 패턴.
  - `Source/`에서 `NETWORK_TEST_CLASS`, `TEST_CLASS`, `IMPLEMENT_SIMPLE_AUTOMATION_TEST`, `AFunctionalTest`를 검색한다.
  - 기존 테스트가 없으면 이 문서의 규칙과 엔진 예제(`<엔진>/Engine/Plugins/Tests/CQTest/Source/CQTestTests/Private/Components/PIENetworkComponentTests.cpp`)를 기준으로 삼는다.
- 프로젝트의 빌드 방법과 테스트 실행 방법을 찾아 각각 그대로 실행할 수 있는 명령 한 줄로 정리한다. 찾지 못하면 `없음`으로 둔다. 언리얼의 기본 형태는 아래 "언리얼 실행 명령"을 따른다.

언리얼에서 추가로 파악할 것:
- 엔진 위치: `.uproject`의 `EngineAssociation` → 레지스트리 `HKLM\SOFTWARE\EpicGames\Unreal Engine\<버전>`의 `InstalledDirectory` → 없으면 `C:\Program Files\Epic Games\UE_<버전>`.
- 네트워크 테스트 도구 존재 여부: `<엔진>/Engine/Source/Developer/CQTest/Public/Components/PIENetworkComponent.h`.
- 테스트 의존성 현황: `<모듈>.Build.cs`에 `CQTest`, `UnrealEd`가 이미 들어 있는지.
- 서버 권위 흐름: 대상 기능에서 아래 네 가지를 찾아 이름을 정리한다.
  - 상태를 바꾸는 서버 함수 (권위 검사가 있는 함수)
  - 그 상태를 담은 복제 프로퍼티 (`Replicated`, `ReplicatedUsing`)
  - 클라이언트 입력이 서버로 가는 RPC (`UFUNCTION(Server, ...)`)와 그 RPC를 가진 소유 액터(폰, 플레이어 컨트롤러 등)
  - 클라이언트에서 상태를 읽는 지점 (복제 값 조회 함수, `OnRep_` 이후 갱신되는 뷰)
- 테스트가 쓸 GameMode: `Config/DefaultEngine.ini`의 `GlobalDefaultGameMode`. 블루프린트면 클래스 경로(`..._C`)를 그대로 적는다.
- 테스트 맵: `Config/DefaultEngine.ini`의 `GameDefaultMap`과 `Content/` 아래 `.umap`. 대상 기능에 필요한 액터가 이미 배치된 맵을 고른다. 맵은 수정할 수 없으므로 필요한 액터가 없으면 테스트가 서버 월드에 직접 스폰할 수 있는지 확인한다.
- 호스트 구조: 코옵 호스트(Listen Server)인지 전용 서버(Dedicated Server)인지.

# 2. 설계 (판단 순서)
항목마다 아래 순서로 따지고, 처음으로 성립하는 단계에서 멈춘다.
1. 정말 필요한가? 요청된 동작을 검증하지 않는 테스트나 헬퍼는 넣지 않는다.
2. 기존 테스트 기반에 이미 있는가? 있으면 재사용한다. 이미 같은 동작을 검증하는 테스트가 있으면 새로 만들지 않는다.
3. 엔진/프레임워크의 기본 테스트 기능으로 되는가? 그걸 쓴다. 언리얼 도구 선택은 아래 "언리얼 테스트 도구 선택"을 따른다.
4. 이미 설치된 의존성으로 되는가? 그걸 쓴다.
5. 여기까지 안 되면 동작하는 최소 구조로 만든다. 헬퍼도 테스트 파일 안에 둔다.

언리얼 테스트 도구 선택:
- 게임 월드가 필요한 흐름은 **CQTest 네트워크 테스트**(`NETWORK_TEST_CLASS` + `FPIENetworkComponent`)를 쓴다. 에디터 안에서 서버 1개와 클라이언트 N개를 자동으로 띄우고, 서버 단계와 클라이언트 단계를 번갈아 실행한다. 패키징이 필요 없다.
  - 클라이언트가 관여하지 않는 서버 전용 흐름도 같은 도구로, 서버 단계만 쓴다.
  - 호스트 구조가 코옵 호스트면 Listen Server, 전용 서버면 Dedicated Server로 설계한다. 클라이언트 수는 시나리오에 필요한 최소로 한다.
- 월드 없이 순수 로직만 검증하는 경우만 CQTest `TEST_CLASS`를 쓴다. E2E 요청이면 보통 해당하지 않는다.
- 쓰지 않는 것:
  - `AFunctionalTest`: 테스트 액터를 맵에 배치해야 해서 맵 수정이 필요하다.
  - Gauntlet: 패키징 빌드가 필요하다.

테스트 의존성 (조건부, 최초 1회):
- 필요한 모듈은 `CQTest`와 `UnrealEd` 두 개다.
  - `CQTest`: `NETWORK_TEST_CLASS`, `FPIENetworkComponent`가 들어 있다. 엔진 내장 모듈이라 플러그인을 켤 필요가 없다.
  - `UnrealEd`: `PIENetworkComponent.h`가 `Editor.h`, `UnrealEdGlobals.h`를 include한다.
  - `NetCore`, `IrisCore`는 넣지 않는다. `Engine` 모듈이 공개 의존성으로 이미 넘겨준다(UE 5.8 `Engine.Build.cs` 기준).
- 1번 항목에서 확인한 현황에 따라 정한다.
  - 둘 다 있으면: `Build.cs` 블록을 스펙에 넣지 않는다.
  - 하나라도 없으면: 1단계에 `<모듈>.Build.cs (수정, 조건부)` 블록을 두고, **빠진 모듈만** 적는다. 에디터 빌드에서만 추가하는 것으로 적는다(`Target.bBuildEditor`). 게임 빌드에는 CQTest가 없기 때문이다.

시나리오 범위:
- 요청된 동작마다 정상 흐름 하나.
- 대상 코드의 입력 검증, 권한/소유권 확인, 오류 처리마다 실패 흐름 하나.
- 모든 조합을 나열하지 않는다.

언리얼 시나리오 규칙:
- 클라이언트가 하는 행동은 실제 경로 그대로 **클라이언트 월드의 소유 액터에서 Server RPC를 호출**하는 것으로 설계한다. 서버 함수를 직접 불러 클라이언트 행동을 대신하지 않는다.
  - 예외: 그 시나리오의 검증 대상이 클라이언트 경로가 아니고, 사람이 개입해야 하는 행동(UI 버튼 등)을 건너뛰기 위한 경우만 서버 함수를 직접 부른다. 이때 시나리오에 `서버 대행`이라고 적는다.
- 기대 결과마다 **어느 쪽에서 관찰하는지**(`서버`, `클라0`, `모든 클라`)를 적는다. 서버에서 바뀐 상태가 클라이언트에 복제되는지 검증하는 것이 이 도구를 쓰는 이유이므로, 상태를 바꾸는 정상 흐름에는 클라이언트 쪽 관찰을 넣는다.
- 권한 검사 시나리오(클라이언트 월드에서 서버 함수를 직접 호출 → 거부, 잘못된 ID로 RPC 호출 → 서버 상태 불변)는 대상 코드에 해당 검사가 있을 때 예외 흐름으로 넣는다.
- 게임 진행(NPC 이동, AI 판단 등)을 기다리는 시나리오에는 제한 시간을 적는다. 예: `제한 60초`. CQTest는 기본 제한 시간이 없어서, 적지 않으면 실패 시 테스트가 끝나지 않는다.
- 서버와 클라이언트의 객체는 서로 다른 인스턴스다. 시나리오에서 대상을 가리킬 때는 포인터가 아니라 양쪽에서 같은 값인 ID(예: AssignmentId)로 적는다.
- 무작위로 결정되는 값(예: 무작위 퀘스트 선택)은 제품 코드를 고쳐 고정할 수 없다. 기대 결과를 특정 값이 아니라 그 값이 따라야 하는 조건이나 상태로 적는다.

금지:
- 내부 구현(비공개 함수, 내부 상태)을 직접 검증하는 테스트. 외부 진입점으로 구동하고 외부에서 관찰한다.
  - 언리얼에서 외부 관찰 지점은 공개 조회 함수와 복제 프로퍼티다.
- 테스트를 위해 제품 코드에 훅, 접근자, `_API` 공개, 테스트 전용 분기를 추가하는 것
- 테스트 대상 자체를 목(mock)으로 바꾸는 것
- 한 번만 쓰이는 테스트용 추상화, "나중을 위한" 테스트 뼈대
- 고정 시간 대기. 조건을 기다리고 제한 시간을 둔다.

반드시 유지:
- 테스트마다 자기 상태를 준비하고 정리한다. 테스트 사이에 상태를 공유하지 않는다. 테스트 메서드마다 PIE 세션을 새로 띄우는 구조로 설계한다.
- 실제 사용자 데이터, 저장 파일, 외부 서비스를 건드리지 않는다.
- 요청에 명시된 모든 동작 (0번 항목 때문에 제외한 것은 승인 때 보여준다)
- 테스트 파일은 기능별 폴더에 둔다: `Source/<모듈>/Tests/<기능>/`. 모듈 루트에 바로 두지 않는다.
- 테스트 경로 이름은 `<프로젝트>.<기능>.<그룹>` 형태로 해서 테스트 명령의 필터로 이 테스트만 골라 실행할 수 있게 한다.
- 테스트의 모든 단계에 설명 문자열을 붙이도록 설계한다. CQTest가 단계마다 시작과 끝을 로그에 남겨서, 사용자가 로그로 테스트 진행을 따라갈 수 있다.

기대 결과:
- 요청에 기대 결과가 명시되지 않아 현재 코드의 동작에서 가져온 기대 결과에는 `코드 기준`을 붙인다. 현재 코드가 틀렸다면 테스트도 틀리므로 사용자가 승인 때 확인해야 한다.

# 언리얼 실행 명령
`<엔진>`, `<프로젝트 루트>`, `<프로젝트>`, `<모듈>`은 1번 항목에서 찾은 실제 값으로 바꿔 한 줄로 적는다. `{LOG_DIR}`은 그대로 둔다. 구현 에이전트가 실행할 때마다 로그 폴더 경로로 바꾼다.
- 빌드: `"<엔진>/Engine/Build/BatchFiles/Build.bat" <모듈>Editor Win64 Development "-Project=<프로젝트 루트>/<프로젝트>.uproject" -WaitMutex`
- 테스트: `"<엔진>/Engine/Binaries/Win64/UnrealEditor.exe" "<프로젝트 루트>/<프로젝트>.uproject" <맵 경로> -ExecCmds="Automation RunTests <테스트 경로 필터>" -TestExit="Automation Test Queue Empty" -unattended -nosplash -nopause -log -abslog="{LOG_DIR}/test.log" -ReportExportPath="{LOG_DIR}/report"`
  - `<맵 경로>`는 `/Game/...` 형식이다. 네트워크 테스트는 에디터에 열린 맵으로 PIE를 띄우므로 맵을 명령에서 지정한다.
  - 네트워크 테스트는 에디터 뷰포트가 필요하므로 창 없는 모드(`-nullrhi`)를 쓰지 않는다. 창은 뜨지만 사람이 조작할 것은 없다.
  - `test.log`: 에디터 전체 로그. 테스트 단계마다 `LogCqTest: Starting <단계 설명>` / `Finished <단계 설명> after N milliseconds`가 남는다.
  - `report/`: 테스트별 통과·실패와 오류 메시지를 정리한 자동화 리포트(`index.json`, 브라우저로 여는 `index.html`).

# 3. 저장 전 자기 점검
스펙을 저장하기 전에 모든 항목을 다시 확인한다.
- 모든 파일 블록이 `Source/<모듈>/Tests/` 아래 테스트 파일이거나, 조건부 `Build.cs` 블록인지 확인한다. 그 밖의 파일 블록이 있으면 지우고 해당 시나리오를 `제외한 시나리오`로 옮긴다.
- `Build.cs` 블록이 있다면 `Build.cs`를 다시 읽어, 적힌 모듈이 정말 빠져 있는지 확인한다. 이미 있는 모듈은 블록에서 지우고, 모두 있으면 블록 자체를 지운다.
- 같은 동작을 검증하는 기존 테스트나 헬퍼가 있는지 다시 검색한다. 있으면 재사용으로 바꾸거나 시나리오를 지운다.
- 판단 순서 1단계(정말 필요한가)를 다시 적용한다. 통과하지 못하면 지운다.
- 시나리오마다 구동할 진입점과 관찰할 지점이 실제로 존재하고 테스트 파일에서 접근 가능한지 확인한다. 이 스펙이 새로 만드는 테스트 코드는 예외다.
  - 클라이언트 행동에 쓰는 Server RPC가 실제로 있고, 테스트가 클라이언트 월드에서 그 RPC를 가진 소유 액터에 접근할 수 있는지 확인한다.
  - 클라이언트 쪽 관찰 대상이 실제로 복제되는 프로퍼티인지 확인한다.
- 시나리오마다 기대 결과가 구체적인 값이나 상태로 적혀 있고, 관찰하는 쪽(서버/클라)이 적혀 있는지 확인한다. "정상 동작함" 같은 표현은 고친다.
- 게임 진행을 기다리는 시나리오에 제한 시간이 적혀 있는지 확인한다.
- 재사용 항목의 위치가 실제로 존재하는지 확인한다.
- 파일 간 호출 관계의 이름이 양쪽 파일에서 일치하는지 확인한다.
- 각 단계가 끝났을 때 빌드가 깨지지 않는지 확인한다. 깨지면 단계를 다시 나눈다.
- 빌드 명령과 테스트 명령에 쓰인 경로(엔진, `.uproject`, 맵 에셋)가 실제로 존재하는지 확인한다. 이 스펙이 새로 만드는 경로와 `{LOG_DIR}`은 예외다.

# 4. 스펙 형식
- 파일 블록을 구현 단계별로 묶는다. 단계마다 첫 줄에 `[N단계]`를 쓰고, 그 아래에 해당 파일 블록을 둔다.
  - 다른 파일이 호출하거나 참조하는 파일(헬퍼, 테스트 기반, `Build.cs`)을 먼저 둔다.
  - 같은 단계 안의 파일끼리는 서로 의존하지 않는다.
  - 서로 의존하는 파일은 같은 단계에 묶는다.
  - 단계 사이는 빈 줄 두 개로 구분한다.
- 파일마다 블록 하나를 만든다. 첫 줄은 파일 이름과 상태다.
  - 예: `Tests/Quest/QuestNetworkTest.cpp (신규)`, `Tests/Quest/QuestNetworkTest.cpp (수정)`, `Asteria.Build.cs (수정, 조건부)`
- 헬퍼와 `Build.cs` 블록: 멤버 변수와 함수를 한 줄에 하나씩 쓴다.
  - 형식: `이름: 역할 설명 - 관계 (상태)`
  - 상태: `신규` / `수정` / `재사용: 파일경로`, 요청에 없지만 꼭 필요한 항목에는 `추가`를 붙인다. `수정`은 테스트 파일에만 쓸 수 있다(`Build.cs`는 `수정, 조건부`).
- 테스트 블록: 첫 줄 아래에 네트워크 구성을 한 줄로 쓰고, 그 아래에 시나리오를 한 줄에 하나씩 쓴다.
  - 네트워크 구성 형식: `구성: <Listen Server | Dedicated Server>, 클라 N, GameMode <클래스 경로>, 테스트 경로 <프로젝트.기능.그룹>`
  - 시나리오 형식: `이름: 준비 → 행동 → 기대 결과 (종류)`
  - 행동과 기대 결과에는 실행하거나 관찰하는 쪽을 `[서버]`, `[클라0]`, `[모든 클라]`로 붙인다. 기다리는 단계에는 `제한 N초`를 붙인다.
  - 종류: `정상` / `예외`. 요청에 없지만 필요한 시나리오에는 `추가`, 코드에서 가져온 기대 결과에는 `코드 기준`, 서버 함수로 클라이언트 행동을 대신하는 시나리오에는 `서버 대행`을 붙인다. 예: `(예외, 추가, 코드 기준)`
- 블록 사이는 빈 줄로 구분한다.
- 무엇을 검증하는지만 쓰고, 어떻게 구현하는지는 쓰지 않는다. 코드, 함수 본문, 의사 코드는 넣지 않는다.
- 파일 맨 위에 아래 세 줄을 쓰고 빈 줄을 둔다. 그 외에는 단계 표시와 파일 블록만 쓴다.
  - `요청: <요청 원문>`
  - `빌드: <빌드 명령 또는 없음>`
  - `테스트: <테스트 실행 명령 또는 없음>`

형식 예시 (`Build.cs`에 두 모듈이 모두 빠져 있는 경우):

[1단계]
Asteria.Build.cs (수정, 조건부)
PrivateDependencyModuleNames: 에디터 빌드에서만 CQTest, UnrealEd 추가 (수정, 조건부)


[2단계]
Tests/Quest/QuestNetworkTest.cpp (신규)
구성: Listen Server, 클라 1, GameMode /Game/Blueprints/BP_GameMode.BP_GameMode_C, 테스트 경로 Asteria.Quest.Network
클라 수주: [서버] NPC 제출로 State=Submitted인 Assignment 생김(제한 60초) → [클라0] 복제로 같은 AssignmentId가 Submitted로 보임 → [클라0] 소유 폰의 Server_AcceptQuestAssignment 호출 → [서버] State=Accepted, [클라0] State=Accepted(제한 10초) (정상)
클라 권한 없음: [서버] Submitted Assignment 있음 → [클라0] 클라 월드의 QuestService에서 AcceptQuestAssignment 직접 호출 → [클라0] false 반환, [서버] State=Submitted 유지 (예외, 코드 기준)
없는 ID 수주: 세션 시작 → [클라0] 존재하지 않는 AssignmentId로 Server_AcceptQuestAssignment 호출 → [서버] QuestAssignments 변화 없음 (예외, 추가, 코드 기준)

# 5. 스펙 저장
- 프로젝트 루트는 `git rev-parse --show-toplevel`의 결과로 정한다. git 저장소가 아니면 현재 작업 디렉토리를 쓴다.
- 프로젝트 루트 아래 `impl-for-test/` 폴더에 `YYYY-MM-DD-<기능-이름>.md`로 저장한다. 폴더가 없으면 만든다.
  - `<기능-이름>`은 테스트 대상을 나타내는 짧은 영어 kebab-case 이름이다. 예: `2026-09-23-guild-commission-e2e.md`
  - 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 끝에 `-2`, `-3`을 붙인다.
- 테스트 로그는 `impl-for-test/logs/<스펙 파일 이름(확장자 제외)>/` 아래에 쌓인다(7번 항목).

# 6. 구현 전 승인
- 저장한 스펙 파일의 경로와 전체 내용을 출력한다. 아래 항목은 따로 모아 한 번 더 보여준다.
  - `Build.cs (수정, 조건부)` 항목: 추가할 모듈과, 이미 있어서 건너뛴 모듈
  - `코드 기준` 시나리오
  - `서버 대행` 시나리오
  - `제외한 시나리오`: 제품 코드나 에셋을 고쳐야만 구동·관찰할 수 있어 뺀 시나리오와 그 이유
- AskUserQuestion으로 구현 진행 여부를 묻는다. 선택지:
  - `구현 진행`: 7번 항목(단계별 구현)으로 넘어간다.
  - `중단`: 스펙 파일 경로만 알리고 끝낸다.
- 사용자가 직접 입력으로 수정 요청을 주면, 스펙을 고쳐 같은 파일에 다시 저장한다. 3번 항목(저장 전 자기 점검)을 다시 거친 뒤, 바뀐 내용을 출력하고 같은 질문을 다시 묻는다.
- 사용자가 스펙 파일을 직접 고쳤을 수 있으므로, 승인 후에는 파일을 다시 읽어 최신 내용을 기준으로 삼는다.

# 7. 단계별 구현
- 시작 전에 `UnrealEditor` 프로세스가 떠 있는지 확인한다. 떠 있으면 에디터가 프로젝트 DLL을 잡고 있어 빌드가 실패하므로, AskUserQuestion으로 사용자에게 에디터를 닫아 달라고 요청한다. 직접 종료하지 않는다. 닫힌 것을 확인한 뒤 진행한다.
- 1단계부터 순서대로, 단계마다 Agent 도구로 `impl-for-test-unreal` 서브 에이전트를 하나씩 호출한다. `run_in_background: false`로 호출해 이전 단계가 완전히 끝난 뒤 다음 단계를 시작한다.
- 각 호출에 넘기는 프롬프트:
  - 스펙 파일의 절대 경로
  - 구현할 단계 번호
  - 이전 단계 보고서의 "스펙과 달라진 점" (1단계는 없음)
- 아래 경우에는 다음 단계로 넘어가지 않고 멈춘다.
  - 빌드 실패, 구현 불가, 테스트 실행 불가
  - 테스트 파일 밖의 파일을 고쳐야만 진행할 수 있는 문제
  - 스펙 자체를 고쳐야 하는 문제 (스스로 고치지 않는다)
  - 테스트 실패 중 `시나리오 문제` 또는 `환경 문제`
- 테스트 실패 중 `코드 버그`는 멈추지 않는다. 제품 코드의 결함을 찾아낸 결과이므로 최종 보고에 모은다.

# 8. 최종 보고
- 스펙 파일 경로
- 테스트 실행 명령
- `Build.cs` 처리 결과: 추가한 모듈 / 이미 있어서 건너뜀
- 단계마다: 구현한 파일, 스펙과 달라진 점, 빌드 결과, **로그 폴더 경로**(`test.log`, `build.log`, `report/index.html`)
- 시나리오마다: 통과 / 실패(분류와 원인, 원인이 보이는 `test.log` 줄)
- 멈췄다면 멈춘 단계와 원인

모든 출력은 한국어로 작성한다.
